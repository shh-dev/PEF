# 디자인시스템 정리 (사용자가 "디자인시스템 정리하자"라고 하면 이 5단계를 한다)

사용자 지정(2026-10-28): 이 말이 나오면 아래 5단계를 **전부 포함**해서 순서대로 진행한다. 대상은 현재 작업 중인 앱이다(PEF 저장소 자체가 아님).
기능은 바꾸지 않는다. 바꾸는 것은 시각 값(간격·크기·색·글자·모서리·그림자)과 그 값을 담는 공통 부품의 구조뿐이다.

## 시작 전

- 대상이 웹앱이 아니면(데스크톱·모바일 앱) 같은 5단계를 쓰되 5단계 캡처는 사용자가 정한 방법으로 한다.
- 실행 중인 화면이 필요하다: 사용자가 준 주소, 또는 승인받아 띄운 로컬 개발 서버. 로그인이 필요한 화면은 사용자가 로그인 상태 주소를 주거나 직접 열어 확인한다.
- `pef shots` 에는 `playwright-core` 와 Chrome 이 필요하다. 없으면 사용자에게 설치 승인을 받는다.
- **가장 먼저 변경 전 캡처를 남긴다:** `pef shots <주소> --label before --out .pef/shots`
- 수정은 사용자가 승인한 범위만. 단계마다 `pef checkpoint` 로 마감하고 점수표(이전 → 지금)를 보고한다.

## 1단계. UI 감사 (Audit) — 전체 화면의 간격·정렬·크기·색상·타이포 불일치 수집

- 값 재고: `pef design <앱 폴더> --out .pef/design` → 색·글자 크기·여백·모서리 고유 개수, 많이 쓰이는 값, 가까운 표준값, 토큰 사용 비율(`design-inventory.md`). 자동 점검 `pef audit` 의 V-01~V-06 과 같은 근거다.
- 화면별 불일치 수집: `pef shots` 로 찍은 캡처와 코드에서 같은 역할인데 다르게 생긴 것(버튼 3종, 카드 간격 제각각, 제목 크기 제각각 등)을 화면별로 적는다. 중복 부품은 V-09.
- 모바일 문제는 `pef touch` 결과(R-02, R-05, R-06, TC-01~03)를 함께 담는다.
- 산출물: `.pef/design/audit.md` — 화면 · 문제 · 근거 값 · 심각도(Suspected) 표. 사용자에게 상위 문제를 보고하고 2단계로 갈지 확인.

## 2단계. 디자인 토큰 고정 — spacing, radius, typography, color, shadow 규칙 정의

- 1단계 재고의 "가까운 표준값"을 출발점으로 **토큰 표 초안**을 만든다.
    - spacing: 4/8 눈금(예: 4·8·12·16·24·32·48)
    - radius: 3~4단계(작음·보통·큼·원형)
    - typography: 크기·굵기·행간 스케일(예: 12·14·16·20·24·32)
    - color: 브랜드·중립(회색 단계)·의미(성공·경고·오류·정보), 대비 4.5:1 확인
    - shadow: 2~3단계
- 토큰은 앱이 쓰는 방식으로 정의한다(CSS 변수, Tailwind theme, TS 상수 등). 이미 있는 토큰 파일이 있으면 그것을 확장한다.
- **사용자 승인 후** 적용: 하드코딩 값을 가까운 토큰으로 치환한다. 한 번에 다 바꾸지 말고 영역(컴포넌트·페이지)별로 나눠서, 치환마다 `pef shots` 로 변화를 본다.
- 눈금 밖 값을 억지로 맞추면 화면이 바뀐다. 바뀌어도 되는지(의도한 변경)는 5단계 비교에서 사용자와 확인한다.

## 3단계. 공통 컴포넌트 정리 — Button, Input, Card, Dialog, Table, PageHeader 등 통합

- 같은 역할을 하는 중복 구현을 찾아(예: 버튼 3종) 하나로 합친다. 우선순위: Button, Input, Card, Dialog, Table, PageHeader, 그다음 Select·Tabs·Toast·Badge 등.
- 각 부품: 변형(variant)·크기·상태(기본·호버·포커스·비활성·로딩·오류) 규칙을 정하고 토큰만 쓰게 한다. 접근성(키보드·포커스 링·라벨)과 터치 크기(≥ 24px, 권장 44px)를 함께 확인한다.
- 기존 사용처를 한 부품씩 교체하고, 교체마다 테스트와 `pef shots` 로 확인한다. 교체 목록(어디를 바꿨나)을 남긴다.
- 기능(클릭 동작·데이터)은 건드리지 않는다.
- 후보 기반: React+Tailwind 앱에서 공통 컴포넌트가 없으면 shadcn/ui 를 기반으로 쓸 수 있다(조건은 `docs/SKILLS.md` 의 "shadcn/ui 도입 조건"). 도입은 사용자 승인 후, 한 부품씩.

## 4단계. 레이아웃 표준화 — 사이드바, 콘텐츠 너비, 페이지 헤더, 그리드 규격 통일

- 규격을 정한다: 사이드바 폭(펼침·접힘)·콘텐츠 최대 너비·좌우 여백·페이지 헤더 구조(제목·설명·액션 위치)·그리드(열 수·간격)·반응형 구간.
- 페이지마다 제각각인 틀을 공통 레이아웃/페이지 헤더 부품으로 모은다. 같은 종류의 화면(목록·상세·폼)은 같은 틀을 쓴다.
- 모바일 크기에서 `pef touch` 로 잘림·스크롤·키보드 가림을 다시 확인한다.

## 5단계. 시각적 검증 자동화 — Playwright 스크린샷으로 변경 전후 비교

- 도구: `pef shots <주소> --label after-N --out .pef/shots` 로 같은 화면을 다시 찍고, `pef shots-diff before after-N --out .pef/shots` 로 비교한다. 바뀐 화면은 빨간 표시 이미지(`__diff.png`)와 `summary.md` 로 남는다.
- 데스크톱(1440)·모바일(390) 두 크기, 애니메이션은 꺼서 흔들림을 줄인다.
- 판정: 바뀐 화면이 **의도한 변경**인지 사용자와 확인한다. 의도하지 않은 변화(레이아웃 밀림, 사라진 요소)는 되돌리거나 고친다.
- 한계를 보고한다: 로그인 화면·눌러야 나오는 팝업·실제 데이터에 따라 달라지는 화면은 캡처되지 않을 수 있고, 가짜 변화(날짜·광고·애니메이션)는 사람이 걸러야 한다.
- 정리가 끝나면 최종 `after` 를 새 기준(before)으로 삼아 두고, 앞으로의 UI 변경에서 같은 비교를 반복할 수 있게 한다(CI 연동은 선택).

## 끝나는 기준

- 5단계 산출물이 모두 있다: 감사 표, 토큰 표(+적용 범위), 공통 컴포넌트 목록(+교체 내역), 레이아웃 규격, 전후 비교 요약.
- 재측정: `pef design` 의 고유 값 개수·토큰 비율이 나아졌는지, `pef audit` 의 V-01~V-06 이 해소됐는지 점수표로 보고한다.
- 남은 일(범위 밖이라 못 한 것, 의도 확인이 필요한 변경)은 "나중에 할 것"으로 정리해 다음 계획으로 보고한다.
