# 4.8 아키텍처

적용: 전 유형 ●
도구 후보: Dependency Cruiser(순환·의존 방향). 없으면 import 그래프를 grep으로 근사하고 신뢰도를 낮춤으로 표기.

| ID | 확인 방법 | 문제 기준 | 기본 심각도 |
|---|---|---|---|
| AR-01 | 폴더/계층 구조와 실제 import 방향 대조 | UI가 DB 직접 접근, 하위가 상위 import | P2 |
| AR-02 | 순환 참조 탐지 | 순환 의존 존재 | P2 |
| AR-03 | 한 파일/모듈의 책임 수 (라우팅+비즈니스+DB 혼재) | 거대 혼합 파일 | P3 |
| AR-04 | 전역 상태·싱글톤 남용, 상태 관리 방식 혼재 | 같은 데이터가 여러 곳에서 관리됨 | P3 |
| AR-05 | API 경계: 요청/응답 타입·검증이 한곳에 있는가 | 화면마다 응답 형태를 가정 | P3 |
| AR-06 | 안 쓰는 추상화·불필요한 계층 (과잉 설계) | 구현체 1개뿐인 인터페이스 다수 등 | P3 |
| AR-07 | 공유 파일 변경 영향 범위(import 수가 큰 파일) | 한 파일이 수십 곳에 결합 | P3 |
| AR-08 | 하드코딩된 환경 의존 값(경로·URL·포트) | 환경별 분기가 코드에 박힘 | P2 |
| AR-09 | 기술부채 표식(TODO/FIXME/HACK) 수·오래됨 | 방치된 핵심 TODO | P4 |
